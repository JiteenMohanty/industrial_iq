# Decisions

This is the reviewer-facing narrative: what DealerPulse is, the choices that shaped it, and the
evidence that the analytics are correct rather than assumed. It is curated, not exhaustive — the
full chronological record of every implementation decision (including the ones that didn't make
the cut here) lives in [`docs/decisions/decision-log.md`](./docs/decisions/decision-log.md), and
the formal architecture decisions are in
[`docs/decisions/architecture-decisions.md`](./docs/decisions/architecture-decisions.md).

## What this is

A five-branch Toyota dealership group has a working sales pipeline but underperforming targets,
and nobody has a single place to see *where* and *why*. DealerPulse answers three questions on
first load, without configuration: which branch is failing, what's the evidence, and what does a
manager do about it right now (a downloadable, actionable list of the affected leads). From there
it supports drilling into any branch, any rep, or any single lead's complete history, and every
view is scopeable by time range and branch and shareable as a URL.

The headline finding the product surfaces: **Lakeside Toyota (Bangalore) contacts only 58.2% of
its leads** (versus 78–82% at every other branch) and **has 33 leads that were never contacted at
all** — the branch isn't converting poorly, it's largely not working its leads in the first place.

## Architecture, briefly

- **Server Components render the dashboard; the dataset never reaches the browser.**
  `lib/data/dataset.ts` is the only module that imports the raw JSON, and it carries a
  `server-only` import specifically so any accidental client-component import fails the build.
  Verified directly, not just assumed: after every build, `.next/static` is grepped for dataset
  content (`"Lakeside Toyota"`, `"customer_name"`) and must return nothing.
- **The URL is the only source of view state.** Time range, branch selection, and every
  drill-through carry their state as query parameters, parsed by one `parseFilters` function that
  never throws — an unrecognised or malformed URL silently renders the default view rather than
  erroring. There is no client-side filter store or context provider; copying a URL into a fresh
  browser reproduces the identical view and identical figures.
- **Three distinct data scopes, not one.** The single input to every analytics and insight
  function (`AnalyticsContext`) carries three separately-filtered views of the same dataset:
  metrics scoped to the reader's time range and branch selection, problem-detection leads scoped
  to branch only (so a narrow time window can never hide an active problem), and group-wide
  figures used as comparison baselines regardless of any filter. Conflating these was identified
  early as the single most likely correctness bug in the build (see ADR-0005) — a branch's contact
  rate is meaningless without the unfiltered group figure to judge it against, and a narrow time
  window must never make a real problem disappear from the alert feed.
- **Nine fixed-threshold detection rules, ranked by a total order.** Every alert is generated by
  one of nine rules (never-contacted, contact-rate, stuck-orders, cold-leads, funnel-collapse,
  rep-outlier, lost-reason, channel-quality, delay-reason) against fixed, spec-approved thresholds
  — never adaptive or tuned to force output. Alerts rank by severity, then financial impact, then
  a stable id tiebreak, so the ranking is identical on every run regardless of rule execution
  order.

## Time semantics (per-metric, not uniform)

A dashboard that applies one time filter uniformly to everything produces a subtly wrong story.
DealerPulse uses three different rules, chosen per metric class:

| Metric class | Scoped by | Why |
|---|---|---|
| Lead counts (conversion rate, funnel population) | `created_at`, within the selected window | A lead belongs to the period it entered the pipeline |
| Revenue and delivered units | `delivery_date`, within the selected window | Revenue is recognised when a deal closes, not when the lead started |
| Problem detection (every alert in the Action Center) | **Not scoped by the time window at all** — branch selection only | A real, ongoing problem (33 never-contacted leads at Lakeside) must not disappear because a reader happened to select "last 30 days" |
| Structural/comparison views (the funnel, branch delivery performance, branch/rep comparison grids) | Full history, unfiltered | A side-by-side comparison across branches or the group funnel shape is only meaningful measured on the same basis for every entity |

The practical consequence: changing the time range on the Overview page moves the KPI tiles and
the trend chart, but never changes which alerts are showing or their ranking. This is deliberate,
tested (`tests/filters/scoping.spec.ts`), and stated explicitly in the product wherever it might
otherwise look like a bug.

## Verification, not assumption

Every headline figure in this product was recomputed directly from `dealership_data.json` rather
than trusted from the original planning brief — and that check caught real errors before they
became test fixtures:

- **Group target attainment is 11.2%, not ≈13%.** The planning brief's own stated inputs (160
  delivered units against a 1,426-unit target) don't arithmetically produce 13% — that was a
  planning-time error, caught before a single test was written against it, and the project's
  constitution (its own governance document, pinning verified figures) was formally amended to
  match the correct number.
- **Losses by starting stage went through two rounds of correction: 118 → 120 → 112 at the `new`
  stage.** The first round was a straightforward arithmetic slip. The second, more interesting one
  was structural: 14 leads in the dataset carry a raw `status` field of `"lost"` with no
  corresponding `"lost"` entry anywhere in their actual stage history — a data-generation artifact
  (all 14 also carry a null loss reason and no activity after their last real transition, both
  corroborating they were never genuinely resolved). The product's own rule — a lead's stage
  progression is derived from its recorded history, never from a flat status field — caught this
  automatically once applied consistently, correcting the total from 288 raw-status losses to 274
  genuine ones.
- **The oldest stuck order is 195 days, not 194.** This one went the other direction: a
  planning-time verification script (PowerShell, parsing UTC timestamps) implicitly converted
  timestamps to the local system timezone before comparing dates, silently shifting the answer by
  a day. The original 195 was right all along; re-deriving it with the actual shipped
  TypeScript/UTC-explicit logic — the same code path the product runs — caught the discrepancy.
- **The never-contacted alert rule needed its scope broadened, correcting the spec itself.** As
  originally specified, the rule only counted leads that were both never-contacted *and* still
  open. Checked directly against the data before writing the rule: every one of Lakeside's 33
  never-contacted leads is already closed as lost, and group-wide only 5 leads total meet the
  narrower definition — not enough to trigger the rule for any branch, ever. The rule (and the
  spec) were corrected to count every never-contacted lead regardless of current status, which is
  also what actually surfaces the product's central finding.

The pattern across all four: a number was checked against the real dataset (or the real shipped
code) before being trusted, not after.

## Known limitations

Stated plainly rather than left for a reviewer to discover:

- **Not-found pages render correct content but return HTTP 200, not 404.** `/branches/{unknown}`
  and `/reps/{unknown}` correctly show a "not found" message (confirmed via a `noindex` meta tag
  and the actual rendered text), but the raw HTTP status doesn't reflect it on these dynamically
  rendered routes — a known limitation of how Next.js's App Router streams responses, not
  something fixable without disproportionate effort for a fixed-scope build. See the decision log
  for the full trace.
- **The shell's branch filter dropdown is inert on the two single-entity detail pages**
  (`/branches/[branchId]`, `/reps/[repId]`) — those pages scope themselves from their own URL path
  and ignore the shared `?branch=` query control. It's a minor, honest rough edge rather than a
  broken control.
- **Responsive layout (SC-009) and the accessibility pass (FR-037) were verified by structural
  code review** — no fixed-pixel widths, every table wrapped in its own scroll container rather
  than the page scrolling, every chart in a fluid container, every interactive control using
  native, keyboard-operable HTML elements with visible focus states and accessible names — rather
  than by live browser rendering or an automated audit tool, which wasn't available in the build
  environment. A manual pass in an actual browser at 1440/1024/768px, plus a real automated
  contrast/keyboard audit, is recommended before treating this as fully verified.
- **The FR-009b "branch with no detected problems" empty state was verified by code inspection,
  not a live example** — every one of the five real branches currently has genuine alerts, so no
  branch in this dataset naturally exercises that empty-state path today. The code handles it
  correctly (`InsightFeed`'s branch-aware message); it simply has no real case in this dataset to
  demonstrate it against.
